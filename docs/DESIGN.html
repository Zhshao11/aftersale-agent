0先读这页：五分钟看懂整个系统

如果只读一节，读这节。后面所有章节都是在展开这页的内容。

一句话

用户在聊天框里说「帮我把那个耳机退了」，系统不会让大模型直接去改订单。 大模型只负责两件事：理解用户想干什么、写出一份操作计划。 至于「这份计划能不能执行、什么时候执行、执行失败了怎么办」，全部由确定性代码决定。

0.1 系统有两条完全不同的处理路径

一条消息进来，系统先判断它是查询还是写操作。这两类的处理方式截然不同， 这是理解整个系统的第一把钥匙。

0.2 写操作为什么必须分三段

你可能觉得「让模型直接调用取消订单的工具」更简单。是的，更简单——但那样就有一个问题： 模型说取消就得取消，没有任何东西挡在中间。而模型是会出错的（它会幻觉、会误解、 会被注入），一旦它出错，用户的订单已经没了。

三段式的设计是把「谁说了算」重新分配：

写操作三段式的职责划分
阶段谁负责做什么为什么是它
① 规划 大模型只会「翻译」 把「不想要了」翻译成 cancelOrder + 订单号 + 原因，写成一个 JSON 计划 自然语言的模糊性只有模型能处理
② 校验 确定性代码 订单存不存在、是不是本人的、符不符合售后政策——三道检查全过才落库 规则必须可验证，不能靠模型「记得」
③ 确认 用户本人 看到计划卡片，点确认；金额 ≥ $500 要点两次 资金操作的最后一道闸必须是人
④ 执行 执行器 幂等、超时二分、失败重试、崩溃续跑 可靠性与模型无关，纯粹是工程问题
关键设计

模型从头到尾没有「执行」这个动作的选项。 写工具（cancelOrder 等三个）注册在 executor/WriteToolRegistry 里， 而模型能看到的工具列表只有 agent/ReadToolBundle 里的三个查询工具。 模型就算被提示词注入攻击，也没有一个「调用了就真退款」的函数可以调——因为它拿不到那个函数。

0.3 一笔订单的完整旅程（具体例子）

用户 U001 说「我的耳机不想要了，帮我退了吧」。他有一笔 ORD20260901001，$89.99，无线蓝牙耳机，状态 PAID（已付款未发货）。

1问题定义与设计目标

先清楚要解决什么问题，才能理解后面每个设计决策为什么长这样。

1.1 场景与风险

电商售后客服是一个「模型犯错代价不可逆」的场景。用户说「帮我退掉」， 背后牵连的是资金回流、库存变更、客诉记录。这类操作有三个特点：

  • 不可撤销——钱退出去就退不回来了，不像发错一条消息可以撤回。
  • 有归属边界——只能操作自己的订单。让模型来判断「这笔订单是不是你的」是不可接受的。
  • 有业务规则——「已发货的订单不能取消」「退款要在收货 7 天内」，这些规则是业务的，不是模型的常识。

1.2 三个必须解决的问题

1.3 六条设计原则

从上面三个问题推导出六条贯穿全项目的原则，后文每个决策都能追溯到其中一条。

#原则含义与落地方式
P1能力最小化 模型只拿到完成它那份工作所必需的能力，多一点都不给。落地：只挂载 4 个只读工具，全部 归属于"查"这一类，写能力一个都不给。
P2能用代码就别用模型 凡是规则确定、可以用代码写的判断，一律不用提示词。落地：订单号用正则提取，归属和政策用纯代码。
P3副作用必须过闸 任何会改变外部状态的动 作，之前必须有一个人工的或确定性的闸门。落地：确认门 + 大额二次确认。
P4结果未知 ≠ 失败 超时后不能假设「没成功所以重试」，因为可能「已经成功只是没收到回复」。落地：超时结果二分 + 对账。
P5崩溃后要还知道有事没做完 恢复的前提不是「能重跑」，而是崩溃后还能发现「有个计划执行到一半」。落地：状态独立提交。
P6控制权必须在自己手里 影响可靠性保证的循环不能交给框架。落地：只读路径也用自研循环，不用框架托管。
为什么单独立一条 P6

P6 看起来像是技术偏好，其实是安全要求。如果你用一个把循环藏在内部的框架， 那么「最多几步」「token 花多少」「超时怎么处理」你都说不出准确答案—— 这些是可靠性保证的组成部分，不是实现细节。说不清的东西没法验证，没法验证的东西不能宣称。

agent/		 意图路由、查询循环、计划生成、确认状态机 不直接调用写工具，不做事务控制
执行层
executor/		 幂等、重试、对账、崩溃续跑、事务边界 不生成计划，不判断政策（政策在工具层再校验一次）
工具层
tools/		 单个业务操作的自包含实现（含政策与归属校验） 不做重试、不做幂等（那是执行层的职责）、不知道 Plan 的存在
数据层
repo/		 持久化访问 不含业务逻辑
一个容易被忽略的设计

工具层自己也要做政策校验，尽管编排层在生成计划时已经校验过一次。 这不是重复劳动，是纵深防御：计划生成到执行之间可能隔了几分钟， 订单状态可能已经变了；而且执行层可能被 /api/executor/resume 从任意时间点唤起， 那时候它拿到的是一个历史计划。工具层的校验是最后一道，也是最可信的一道。

3.2 为什么执行日志和轨迹要分成两张表

这是一个看起来可以偷懒的地方：都是「记录发生了什么」，合成一张表不行吗？

不行，因为两张表的语义不同：

3.3 幂等键表：靠数据库而不是靠代码

-- idempotency_keys：唯一索引 = 构造性防重放
CREATE TABLE idempotency_keys (
    idempotency_key   VARCHAR(128) PRIMARY KEY,   -- 格式 planId:stepId:attempt
    plan_id           BIGINT NOT NULL,
    step_id           BIGINT NOT NULL,
    attempt           INT NOT NULL,
    result_status     VARCHAR(16) NULL,           -- SUCCESS / FAILED / UNKNOWN
    result_json       JSON NULL,                  -- 冲突时用于回放
    created_at        DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB;
一个真实的坑

最初用 JPA 的 save() 来写幂等键，发现冲突根本不会触发——因为 JPA 对「主键已存在」的实体走的是 merge（更新），而不是 insert，唯一索引自然不会报错。 这是一个典型的「你以为你在测唯一性，其实你在测更新」的陷阱。 现在改成 JdbcTemplate 的原生 INSERT，让冲突以 DuplicateKeyException 的形式暴露出来。

4链路一：查询应答

「我的订单到哪了」这类问题走这条路。无副作用，所以策略上可以放开一些。

4.1 这条链路要解决什么

查询看起来是最简单的部分——查个订单详情而已。但真正的问题是： 模型可能会编。你问「我的耳机到哪了」，模型完全可能一本正经地回答说 「您的订单已发货，预计明天送达」——而它根本没调用任何工具，那段话是它编的。

同时，一个查询可能要多轮才完成：「查一下我最近买的那个咖啡机的物流」——模型得先查订单、拿到订单号、再查物流。这就是 ReAct 循环（推理-行动交替）要解决的问题。

4.2 自研 ReAct 循环

关键在于：这个循环是自己写的，不是框架的。

4.3 为什么要自己写，不用框架的循环

Spring AI 提供了现成的 ChatClient.tools(...).call()，它会自动跑 ReAct 循环。 用起来很省事，但会失去四样东西：

控制项框架托管时会怎样自研后能得到什么
步数循环在框架内部，你不知道跑了几轮maxSteps=6，超了返回 MAX_STEPS 并说明
成本拿不到累计 token每轮累加，超 12000 主动停下
时延只有总耗时，没有分段单次调用 20s 上限 + 整体 30s 上限，分两级
重复动作模型可能反复调同一个工具同参数重复 2 次即终止
实现方式

自研的实现手段是给 Spring AI 传一个 internalToolExecutionEnabled(false) 的选项 （见 LlmPort.SpringAiLlmPort.callOnce）。这样框架只负责发一次请求、解析一次响应， 不再替我们跑循环。「要不要继续调工具」这个决定权回到我们手里，上面四个控制项才有可能存在。

换句话说：不是不用框架，而是只用框架的「通信能力」，不用框架的「决策能力」。

4.4 边界触发时会怎样

一个容易做错的地方：边界触发后如果只是静默返回空，用户看到的是「系统没反应」， 和「正常回答」在体验上分不清，那这个边界等于白设。

所以每一次非正常终止都会生成一句人话说明为什么停：

终止原因触发条件给用户的说明
ANSWERED模型不再调工具（正常路径，返回答案）
MAX_STEPS超过 6 步「这个问题需要更多步骤才能查清（已到 6 步上限）……请把问题拆细一点」
WALL_CLOCK超过 30 秒「这次查询超时了，我没有拿到完整结果，先不下结论」
TOKEN_BUDGET超过 12000 tokens「消耗的上下文超出了预算（约 N tokens），我主动停下来」
REPEATED_ACTION同参数重复调用「我发现自己陷入了重复查询，已主动停下」
FABRICATION_BLOCKED答复含无出处订单号「我没能从系统里确认到这条信息，所以不能给你答复」
贯穿的原则

注意所有兜底话术的共同点：宁可说「我不知道」，也不给一个看起来合理的答案。 在售后场景里，一个编造的「您的订单明天送达」会让用户
——不去联系客服、不去查真实状态、按错误信息做决策。这比直接说「没查到」危害大得多。

5.2 三重校验分别在防什么

校验防止的问题具体实现
工具白名单 模型幻觉出一个不存在的工具（比如 deleteOrder） PlanGenerator.WRITE_TOOLS 是 Set.of 三个名字，解析时任何一个不在集合里就整份计划抛异常

为什么订单号要在代码里先提取一遍

用户消息里已经有订单号了（ORD20260901001），为什么还要让模型再输出一遍？ 因为模型输出的是「计划语义」（要取消、原因是「用户不想要了」），订单号只是它复述的。 既然只是复述，就不要依赖它复述对——所以用正则从用户原话里先提一遍拿到确定的订单号， 再用模型输出的订单号做二次核对。两道都对才继续。

5.4 确认门：为什么大额要点两次

确认门的状态流转（含大额分支）：

大额二次确认背后的判断

单次确认对普通操作够了——用户看得懂「取消这个 $89 的耳机订单」意味着什么。 但 $1599 的操作是另一回事：用户可能在快速点击、可能没看清金额、可能误触。 第二次确认的价值不在于多一次点击，而在于强制用户重新读一遍金额。

阈值定义在配置里（aftersale.confirm-threshold-cents: 50000），不是硬编码。

一个被评测抓出来的设计缺口

「取消」和「退款」看起来是两个不同的操作，所以在最初实现里，只有 refundOrder 会计算金额、 触发大额二次确认。评测跑 $1599 无人机的取消场景时暴露了问题： 取消一个已支付订单 = 全额退款 = 资金回流，风险性质与退款完全相同。 

// PlanService.java —— 修正后的写法
plan.estimatedAmountCents =
    ("refundOrder".equals(firstTool) || "cancelOrder".equals(firstTool))
        ? target.getAmountCents() : null;

教训是：按资金流向定义风险等级，而不是按工具名。 这是那种只有真实跑过才会发现的缺口——纯看代码很难意识到「取消已支付订单」和「退款」在资金维度是同一件事。

6链路三：受控执行与故障恢复

计划确认之后的部分。这是全项目技术上最难、也最值得讲的一节。

6.1 核心难题：超时了，到底成功没成功？

这是分布式系统的经典问题，在「动钱」的场景里尤其致命。考虑这个情形：

6.2 超时结果二分

所以执行器把「失败」拆成了三类，而不是一类：

分类怎么判断处理策略理由
FAILED
可重试		 连接失败、请求未发出之前的错误 换新 attempt 重试，上限 3 次 确定没执行，重试是安全的
FAILED_FINAL
业务拒绝		 政策拒绝、越权、订单不存在、参数非法 立即终止，不重试 这是确定性的拒绝，重试一万次也是同样结果
UNKNOWN
结果未知		 请求已发出但无响应（超时、阻塞） 禁止重试 → 转对账 可能已经成功了，重试会造成重复执行
这条设计的意义

很多系统的失败处理就是「catch 到异常就重试」。在只读场景里这没问题（重查一次没有副作用）， 但在写操作场景里，「统一重试」是一个会制造资金事故的策略。 区分这三类，意味着要理解每一类失败背后「外部世界到底发生了什么」——这是从「会写代码」到 「理解系统」的分水岭。

6.3 对账：怎么判断「上次那笔到底生效了没」

结果未知时不能重试，那怎么办？去查。 每个写工具都有明确的「期望终态」，查一下订单现在是不是已经到那个状态就知道了。

6.4 幂等与崩溃恢复

上面解决的是「结果未知」。还有一类问题：进程本身崩了。 执行到一半被 kill -9，重启之后怎么知道该从哪继续？

这里曾经有个严重的实现缺陷

最初的实现把 plan.status = "EXECUTING" 和整个执行过程放在同一个事务里。 看起来没问题，但后果是：崩溃 → 事务回滚 → EXECUTING 这个标记也没了 → 计划退回 CONFIRMED → resume() 扫的是 EXECUTING，什么也扫不到 → 断点续跑从来没有真正生效过。

同一时期还有第二个问题：幂等键也在那个大事务里，崩溃时一起回滚——意味着重试时没有任何东西能拦住重复执行。 这两个问题的修复方式就是下一节要讲的「事务边界下沉」。

6.5 断点续跑

恢复逻辑本身很简单，前提是数据留对了：

// Executor.resumeAll()：扫描所有 EXECUTING 的计划，逐个续跑
for (PlanEntity plan : planRepository.findAll()) {
    if ("EXECUTING".equals(plan.status)) { execute(plan.id, plan.userId); n++; }
}

// execute() 内部：跳过已成功的步骤，从第一个非 SUCCESS 的步骤继续
for (PlanStepEntity step : steps) {
    if ("SUCCESS".equals(step.status)) continue;   // 断点续跑
    ...
}

可以看到，「续跑」这件事本身只有几行代码。真正难的是让它能工作—— 也就是保证崩溃之后 plans.status 还留着 EXECUTING、已经成功的步骤还留着 SUCCESS。 这部分难度全在事务边界上。

7核心机制：三条构造性保证

这一节是全项目最值得带走的内容。三条机制有共同特征：不依赖模型「守规矩」。

7.1 什么是「构造性」

先区分两种保证方式的根本差别：

提示词级保证构造性保证
做法 在提示词里写「禁止调用写工具」 让模型根本拿不到写工具
失效条件 模型不理解、被绕过、被注入、换了个模型 需要修改代码或数据库才能失效
可验证性 只能抽样测试「它这次听话了没」 可静态验证：工具列表里就是没有那个函数
一句话概括 「我请求它不要」 「它要不到」
为什么这个区分很重要

在只读场景里，提示词级保证是可以接受的——最坏情况是模型说错话，没有实际损害。 但在写操作场景里，「请求模型不要动钱」和「模型动不了钱」是两种完全不同量级的保证。 前者意味着你的安全边界取决于一个概率系统（模型）当次的表现，后者意味着它不取决于此。

7.2 保证一：写工具物理隔离

连带的设计：身份不能由模型提供

只隔离工具还不够。如果工具的签名是 cancelOrder(orderNo, userId)，而 userId 由模型填——那模型填成别人的 ID 就能越权。 

// ReadToolBundle.java —— userId 从 ToolContext 注入，不是模型参数
// 注意方法签名里没有 userId，模型无法传这个参数
public ToolResult getOrder(@ToolParam(description = "订单号") String orderNo,
                           ToolContext ctx) {          // ← 框架注入，非模型可控
    return getOrderTool.getOrder(orderNo, userId(ctx));
}

static String userId(ToolContext ctx) {
    Object v = ctx.getContext().get("userId");
    if (v == null) throw new IllegalStateException("ToolContext 缺少 userId");
    return v.toString();
}

这个方法签名里根本没有 userId 这个参数，所以模型即使想传也无处可传。 身份由编排层在调用前放进 ToolContext。

连带的设计：用户不会主动报订单号

一开始的只读工具集只有 getOrder / getLogistics / getPolicy， 三个全都要求先有 orderNo。这在真实客服场景里是不成立的： 用户说"我最近买的那个咖啡机的物流"，不会附带订单号。原来的做法是模型反问用户要单号—— 但我们实测发现更糟的情况：模型不反问，直接编一个订单号（它会拿上下文里出现过的单号凑）， 然后被反幻觉闸门拦下，用户拿到一句"抱歉没能确认到"。链路是通的，能力是缺的。

补的是 listMyOrders。它的定位很关键：它是"索引"，不是"详情"。 工具只回答"这个用户有哪些订单"（按时间倒序，带商品名/状态/金额/下单时间）， 不替模型判断"哪个是用户说的那个"——那一步是语义判断，是模型该做的事。

设计选择理由
关键词过滤放在工具里，
但"选哪一单"留给模型		 过滤是确定性字符串匹配（代码更可靠）；而"蓝牙耳机"可能指"无线蓝牙耳机"或"降噪头戴耳机"， 这需要语义判断。实测模型会主动列出候选让用户确认，而不是猜一个。
关键词没命中不返回空，
退回最近 N 条 + note 说明		 用户对商品的称呼常与系统记录不一致（"那个咖啡机" vs "全自动咖啡机"）。 返回空会让模型误判"用户没有这个订单"；退回最近订单则给了模型纠错的机会。
条数硬上限 20，默认 5 这是给模型做指代消解用的，不是导出历史。上限防止把上下文塞满、挤掉其他信息。
limit 非法值退化为默认，
不报错		 查询类参数不值得让整次调用失败。写路径的参数校验才必须严格。

权限边界与其它读工具一致：userId 同样从 ToolContext 注入， 签名里没有这个参数，所以模型无法"查别人的订单列表"。

实测效果 「查一下我最近买的那个咖啡机的物流」→ 3 步完成：listMyOrders(keyword=咖啡机) 命中 ORD202609050002 → getLogistics → 答"运输中"。 「我上次买的蓝牙耳机」→ 命中 2 单，模型列出候选请用户确认。 「我买的那个电饭煲」→ 如实说没找到并列出最近订单，没有编造。

7.3 保证二：读侧反幻觉闸门

前面说过，写路径的安全是构造性的：金额取自订单实体、政策查表、归属由注入的 userId 决定， 模型没有「编」的空间。

但只读路径最初只有提示词约束（「禁止编造任何订单号」）。这就是问题所在： 同一个项目里存在两套标准——写路径靠架构，读路径靠模型自觉。

反幻觉闸门

做法：答复中出现的每一个订单号，都必须能在本回合的事实来源里找到出处。 事实来源 = 用户原话 + 本回合所有工具返回内容。找不到出处 = 编造 → 该答复不予采信，降级为兜底话术。

这是纯函数（FabricationGuard.violations(answer, knownFacts)），可独立测试， 不依赖模型配合。 

// FabricationGuard.java —— 核心逻辑就三行
public Set<String> violations(String answer, Set<String> knownFacts) {
    Set<String> cited = extract(answer);   // 答复里出现的订单号
    cited.removeAll(knownFacts);           // 去掉有出处的
    return cited;                          // 剩下的就是编的
}
这个机制的边界（不要过度宣称）

代码注释里明确写了两条限制，值得保留：

  • 只校验订单号这一类强标识实体。金额、日期、人名暂不校验——在没有结构化事实源的情况下， 它们的误报率太高，宁可不做也不要制造假阳性把正常答复拦掉。
  • 这是「降低编造出现在用户可见输出里的概率」，不是「消除幻觉」。 如果工具返回的数据本身就是错的，闸门挡不住。

7.4 保证三：事务边界下沉

这是全项目最微妙的一个设计，也是「崩溃恢复」能不能成立的技术前提。

先看错误的做法

三个类的分工

修复方式是拆成三个类，每个负责一种粒度的提交：

类事务职责与理由
Executor 无事务 只做编排与重试循环。刻意不加 @Transactional——它要保证的是「每次尝试各自独立提交」，自己开了事务就破坏了这个性质。
StepRunner @Transactional
(REQUIRED)		 承担「一次尝试」。把业务写 + 步骤状态 + 执行日志 + 幂等键作为一个原子单元提交。这是最关键的边界。
PlanStateWriter @Transactional
(REQUIRED)		 计划状态迁移。独立提交，保证崩溃后状态标记存活。
两个容易踩的实现细节

① 为什么必须拆成独立的 Bean。 Spring 的事务是靠代理实现的，this.method() 这种自调用不走代理， 注解形同虚设。原实现把 @Transactional 标在 Executor 的私有步骤方法上， 因为自调用而不生效——「每步落账」从来没有真正发生过。

② 为什么用 REQUIRED 而不是 REQUIRES_NEW。 这是刻意的双面考虑：生产环境 Executor 不开事务，所以这里各自成为独立事务并提交（要的就是这个）； 测试环境测试方法自带事务，于是这里并入测试事务、随测试回滚（保住测试隔离）。 如果用 REQUIRES_NEW，测试写入会绕开测试事务污染数据库，反而把测试搞坏。

7.5 三条机制的共同点

  • 都不依赖模型的表现。换一个模型、模型被注入、模型抽风，这三条保证都还在。
  • 都可以被静态验证。不需要跑一万次看它有没有出错——看工具列表、看代码路径、看数据库约束就能确认。
  • 都有明确的失效边界。物理隔离防模型越权，不防代码 bug；反幻觉闸门防订单号编造，不防金额编造；事务边界保证本地一致性，不保证跨系统（真实支付接口）的一致性。

8状态机与事务边界

把散落在各处的状态和事务集中看一遍。

8.1 三层状态

状态字段取值数取值与含义
orders.status 6 PAID · SHIPPED · DELIVERED · CANCELLED · REFUNDED · EXCHANGED
业务实体的状态，由写工具改变
plans.status 8 PENDING_CONFIRM · AWAITING_SECOND_CONFIRM · CONFIRMED · EXECUTING · COMPLETED · FAILED · CLOSED · EXPIRED
计划的流程状态，由 PlanManager 与 PlanStateWriter 改变
plan_steps.status 5 PENDING · RUNNING · SUCCESS · FAILED · UNKNOWN
单步的执行结果，由 StepRunner 改变。UNKNOWN 这一态是关键——它表示「不知道成功没」
为什么 plan_steps 需要 UNKNOWN 这个状态

大多数状态机只有「成功/失败」两态。但在这个场景里，「不知道」是一个必须被显式表达的真实状态—— 它对应的处理策略（禁止重试、转对账、标记待人工）与「失败」完全不同。 如果硬把它归入「失败」，系统就会去重试，然后重复退款。

状态机里少一个状态，往往意味着某类情况被迫被错误归类。

把 trace 放进响应里，是刻意的设计

termination 和 token 用量直接暴露给调用方，理由是： 「这次为什么没答上来」必须当场可见，否则边界触发和正常回答在用户那里长得一样， 边界等于白设。

错误响应

所有异常统一由 GlobalExceptionHandler 产出，含可关联标识：

{ "error": "INVALID_ARGS", "message": "message 最长 2000 字符", "errorId": "e-8f3a2c" }

errorId 同时写进日志，使「用户看到的报错」能对回「日志里的某一行」—— 没有这个标识，线上排障只能靠时间戳猜。

9.3 入参校验

用 Bean Validation 而非手写判空：

public record ChatRequest(
    Long conversationId,
    @NotBlank(message = "userId 必填") @Size(max = 32)      String userId,
    @NotBlank(message = "message 必填") @Size(max = 2000)   String message) {}

手写判空只能覆盖「必填」，覆盖不了长度——超长输入会直接进模型和数据库，那是拿 token 和存储当免费资源用。 这个理由写在了代码注释里。

10.2 只读循环的九个参数

配置项默认值作用与设计理由
max-steps6单次请求最多几步。超了返回 MAX_STEPS 并说明

为什么 call-timeout 与 wall-clock 不能合并

它们防的是两类不同的故障：call-timeout-ms 防「一个请求挂死」， wall-clock-ms 防「每一步都不算慢，但加起来跑了很久」。 少了任何一个，另一类故障就拦不住。代码注释里专门说明了这一点。

工具输出截断为什么要重新包 JSON

直接 substring 截断会把 JSON 切成半截——而模型收到半截 JSON 时更容易编 （它会试图「补全」这个残缺结构）。所以超长时的做法是重新包一层合法 JSON： 

{ "truncated": true, "originalChars": 8420, "preview": "…前 4000 字符…" }

truncated: true 这个标记很关键：它告诉模型「这是残缺预览，不是全部事实」， 而不是让模型以为自己拿到了完整数据。

11.2 包结构的意图

包设计意图
tools/read
tools/write		 读写在包级别就分开。这不是为了好看——ReadToolBundle 只 import tools.read 下的类， WriteToolRegistry 只 import tools.write 下的类。隔离在编译期就成立，不靠运行时检查。
agent/
executor/		 把「决定做什么」（agent）与「怎么可靠地做」（executor）拆开。前者关心语义与安全边界，后者纯粹关心可靠性。 两者的关注点没有交集，混在一起会让两类问题互相干扰。
executor/ 三个类 Executor / StepRunner / PlanStateWriter 的拆分完全是为了事务边界， 不是职责美学。这类拆分是最难凭直觉想到的——它源于「Spring 事务靠代理，自调用不生效」这个具体的技术约束。

12正确性如何被验证

「我实现了 X」和「X 真的生效了」是两件事。这节讲怎么区分。

12.1 三档证据强度

项目里不同能力被验证的强度是不同的，把这一点说清楚比笼统说「都测过了」更有价值。

档位证据形式能证明什么 · 不能证明什么
第 1 档 提示词里写了约束 不构成证据。能证明「我要求模型这样做」，不能证明「模型会这样做」
第 2 档 普通单元测试 能证明逻辑分支正确。但对持久化/恢复类能力无效（见下）
第 3 档 进程级真实实验 能证明系统在真实故障下的行为。持久化、恢复、幂等必须站这一档
一个关键的陷阱：带测试事务的单测证明不了持久性

大多数 Spring 项目的集成测试会给测试方法加 @Transactional，测试结束后自动回滚，保证测试之间不互相污染。 这本身是对的。

但如果被测代码是「崩溃恢复」这类能力，这个做法就失效了—— 因为测试事务会把被测代码的提交也一并回滚。 等于用橡皮擦去证明铅笔写过字。

所以这个项目里的持久性测试（D5DurabilityTest）刻意不加 @Transactional， 并且把「为什么不能加」写进了测试注释。真正证明崩溃恢复的是 scripts/crash_recovery_probe.sh——它对一个真的在执行的进程发 kill -9。

12.2 崩溃恢复实验是怎么做的

这是项目里证据强度最高的一个实验，值得完整看清它的步骤：

#动作断言 / 目的
1启动应用，准备一个两步计划计划状态 PENDING_CONFIRM
2确认并开始执行—
3定向注入 HANG：让第 2 步阻塞制造「第 1 步已完成、第 2 步阻塞中」的窗口
4kill -9 杀死进程不做优雅退出，模拟真实崩溃
5检查数据库现场5 条断言：plans.status=EXECUTING / 第 1 步 SUCCESS / execution_log 1 条 / idempotency_keys 1 条 / 订单已是 CANCELLED
6重启应用，调用 /api/executor/resume返回 {"resumed":1}——找到了那个没做完的计划
7检查续跑结果5 条断言：计划 COMPLETED / 第 1 步日志仍为 1 条（未重复执行）/ 第 2 步执行一次 / 第 2 步副作用生效
这个实验的关键设计

第 5 步的断言是整个实验的核心。它证明的不是「系统恢复了」，而是 「崩溃之后系统还知道有事没做完」——这才是恢复的前提。 第 1 步的 execution_log 只有 1 条，证明续跑时没有重复执行。

这个实验是可重复运行的脚本，退出码 0 表示全部断言通过。也就是说： 任何人拿到这个仓库都能自己跑一遍验证。

12.3 消融评测

评测设计的核心是「同模型、同任务集、同判定规则，只变一个东西」。

三个配置的对照（36 条任务）
配置消融了什么完成率高额操作拦截
V0 基线 变成单环 ReAct 直连，读写工具全挂载 31/35 5/6（缺大额二次确认）
V1 去掉 Plan 级确认门 35/36 5/6（同上）
V2 完整版 — 36/36 6/6

两个值得注意的结论：

  • 越权拦截在三配置下都是 100%。这恰好印证了「安全是构造性保证」—— 因为归属与政策校验在工具层是确定性代码，不依赖模型自觉，所以连基线版本也拦得住。 V2 的增量来自「确认门」和「规划校验」，不是「一个更听话的模型」。
  • V0 的失败集中在故障恢复场景。基线把「失败了怎么重试」交给模型在对话里临场判断， 多轮之后模型会偏离任务；V2 由执行器确定性地处理，所以自愈了。 这是「把可靠性从模型手里拿走」这句话的具体证据。
这个评测的局限（必须说明）
  • V1 → V2 的 +2.8pp 是四项机制的合力（确认门 + 大额分级 + 指纹失效 + 断点续跑）， 四项没有单独关闭做过对照，所以拆不出单项贡献。要做单项归因，需要给指纹失效和断点续跑各补一个消融开关，跑六组配置。
  • 36 条样本属于小样本，判定部分依赖关键词匹配，报告里已如实标注。
  • 报告记录的是单轮结果，LLM 有随机性，补跑取均值会更稳。

13已知边界与设计取舍

明确说出「不做什么」和「哪里不够好」，比声称什么都做了更可信。

13.1 有意的取舍

下面这些不是没做完，是判断了「不做」：

项目决定理由
长期记忆 不做 售后场景的上下文是订单本身，而订单在数据库里、随查随有。 做成向量检索的「记忆层」是包装层，不是能力层——它增加复杂度但不解决这里的真问题。
多 Agent 协作 不做 没有哪个子任务复杂到需要独立 Agent。多 Agent 只有在能产生可测收益时才值得引入， 否则只是把一个模型的问题变成多个模型的问题。
模型微调 / 训练 不做 这个项目的主张是「模型不可信」，既然如此，把安全性寄托在「训练一个更听话的模型」上就自相矛盾了。 应该用工程手段而不是训练手段解决。
复杂前端 从简 演示页用原生 JS 写（14.7 KB），目的是让链路可演示而不是做产品。 前端投入不产生可靠性收益。

13.2 已知缺口

缺口影响说明
/api/selftest 有副作用 中 自检接口会写数据。原设计里它用 rollbackFor = Exception.class 试图回滚， 但对「正常返回」的路径不会回滚——rollbackFor 只扩大异常范围，不会让正常返回回滚。
disable-timeout-classify 未接线 中 开关存在但没有调用点（见 §10.3）。影响：超时二分能力无法单独消融
写路径越权拒绝无审计记录 中 越权时只返回拒绝消息，不写 agent_trace 或 execution_log。 「谁在什么时候试图操作不属于自己的订单」在库里查不到——安全类场景值得补
恢复语义仅限单进程 中 resumeAll() 没有分布式锁。多实例部署时可能重复接管同一计划 （虽然幂等键能兜住重复执行，但会有无谓的并发）
无真实支付/物流对接 低 写工具操作的是本地 orders 表。真实对接会让一致性问题的难度上升一个量级 （跨系统事务无法回滚），当前对账机制正是为此预留的思路，但没被真正考验过
无多租户与鉴权 低 userId 由请求方传入，没有身份认证层。演示场景下可控
无监控告警 低 有轨迹可查（排查型观测），但没有指标聚合与告警（运营型观测）

13.3 文档与实现的一处不一致

如实记录

USE_GUIDE.md 里教演示者用 --aftersale.inject-timeout-after=xxx 来演示超时， 但这个参数在整个项目里只有这一处出现，配置文件里没有、代码里也没有。 按该文档操作会静默无效。正确的做法是用 POST /api/fault?mode=TIMEOUT_UNKNOWN。

13.4 如果继续做，优先级

  1. 补齐可执行示例与干净环境复现记录——这是「别人能不能复现」的问题，成本最低、影响最大。
  2. 给指纹失效与断点续跑补消融开关，跑六组配置——把 V1→V2 的 +2.8pp 拆成单项贡献表。
  3. 补评测口径：端到端耗时、单任务成本、预算超限率。 原料其实都有了（agent_trace.latency_ms 逐节点记录、token 每步记录、终止原因可枚举）， 只差聚合与单价换算。
  4. 修掉 disable-timeout-classify 的接线与 USE_GUIDE.md 的失效参数。
  5. 越权拒绝落审计——安全类项目里这条不该缺。
  6. 依赖锁定（lockfile / wrapper）与配置外置（数据库账密）。
